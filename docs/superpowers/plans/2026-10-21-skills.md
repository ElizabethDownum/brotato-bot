# Brotato Bot Skills Implementation Plan (plan 3 of 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Three Claude Code skills in the project, `brotato-next`, `brotato-decide` and `brotato-advise`, plus a deterministic stagnation check, so the between-run proposal, the mid-run decision prompt and the manual-run advisor all read the same files the harness writes.

**Architecture:** Skills are `SKILL.md` files under `brotato-bot/.claude/skills/<name>/` that point the model at concrete files and templates. Anything that must be deterministic (stagnation verdict, proposal file naming, plan validation) is a Python command the skill calls, not prose the model is trusted to follow. `brotato-decide` shares its system prompt file with the sidecar so there is one source of truth.

**Tech Stack:** Claude Code skills (markdown with front matter), Python 3.12 (existing `brotato_bot` package), pytest.

**Spec:** `<repo>\docs\superpowers\specs\2026-10-21-brotato-bot-design.md`

## Global Constraints

- Skill front matter: `name`, `description` (one line, says when to use it), `model: haiku` for `brotato-next` and `brotato-decide`, `model: sonnet` for `brotato-advise`; `brotato-next` runs on Sonnet when invoked with the argument `sonnet` (`/brotato-next sonnet`), which is the spec's "Sonnet 5.5 on request". Model ids: `claude-haiku-5-5`, `claude-sonnet-5-5`.
- Proposal files: `proposals/<YYYY-MM-DD>-<n:03>.md` with the exact section order: `# Proposal <n>`, `## Target`, `## Next run` (character id, danger, target challenge), `## Plan` (a fenced JSON block that is a valid plan file per plan 1 Task 3), `## Why` (at most three sentences, each citing a file or a dataset fact), `## Risk`, `## Stagnation check` (the verdict line from the Python command, verbatim).
- Stagnation rule (lax): a target is `stagnant` when the last `3` runs on it all ended in death with no improvement in `death_wave` and no improvement in `hp_end` of the last completed wave; after a stagnant verdict the next proposal must change `plan_id` family, `character_id` or the target route; after `2` consecutive stagnant verdicts with material changes, the verdict becomes `escalate` and the proposal must say so in `## Stagnation check` and stop proposing that target.
- Commit messages end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.

## Review Focus

1. `runs/index.json` is empty or missing on the very first proposal: the stagnation command must print `fresh` and the skill must still produce a proposal. (Task 1 test `test_no_runs_is_fresh`.)
2. The plan JSON in a proposal references a character the bot profile has not unlocked: `prepare` must refuse it with the character name. (Task 2 adds `test_prepare_rejects_locked_character` to plan 2's `tests/run/test_prepare.py`.)
3. The advisor is pointed at a state file from profile 1 by mistake: it must still only advise, never write into `requests/`. (Task 4: the skill text forbids writes; the test is a read of the skill file asserting the sentence is present.)
4. Two proposals generated the same day: numbering must continue, not overwrite. (Task 2 test `test_next_proposal_number_increments`.)
5. A mid-run checkpoint arrives after the target fired: the answer must optimise the current character's remaining waves rather than keep chasing the target. (Task 3 prompt text; verified by a fixture run of `decide-once` with `--kind checkpoint`.)
